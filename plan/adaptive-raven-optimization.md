## 目标与验收口径

| 目标 | 验收方式 |
| --- | --- |
| 正确率尽量不降低 | 相同题目、种子、判分器比较优化前后 Adaptive；以原仓库准确率及“正常结束且判对”共同评价，目标是两者均不下降。下降时检查逐题差异，候选暂不升级为默认。 |
| 优于论文主基线 | 在同一测试协议下报告 Native、Cactus、SpecCascade、Adaptive；优先争取在相近质量下超过最快的 Cactus。不能只凭超过旧 Adaptive 宣称超过三个基线。 |
| 速度确实提高 | 同时报告端到端/解码 token/s、平均及中位数请求耗时、输出长度和验证轮成本。第一阶段争取追平 Cactus，第二阶段以比 Cactus 吞吐高至少 5% 为工程目标。 |
| 结论可复现 | 最终固定参数，用 3 个生成种子做配对复测，报告准确率差与吞吐比的置信区间；结果不确定时明确标为证据不足。 |

“正确率不下降”是目标，不是单次测试能证明的数学保证。严格 `####` 最终行正确数、截断率和重复输出用于辅助诊断；boxed 等有效格式不能仅因格式不同被当作数学错误。“未检出显著下降”不等于已经证明质量相同。

旧 Adaptive 的端到端吞吐为 2.828 token/s，Cactus 为 2.988 token/s。保持当前 MAL 时，估算轮成本从 1.222 秒降至约 1.156 秒可追平 Cactus，降至约 1.101 秒可争取快 5%；这是推导的优化预算，最终以新实测为准。

## 每阶段的质量检查

- **实现优化：** 使用相同前缀和候选检查 Q、接受概率、修正分布及分支 KV；随机数消耗的变化需解释。遇到语义不一致先修复，不能用一次准确率正常替代验证。
- **参数调整：** 截断短请求只用于测速；质量检查沿用原版 2048 输出上限。候选出现准确率或正常结束判对数下降，先检查错误案例并补充校准证据；未经验证不进入最终配置。
- **正式结果：** 参数冻结后完整报告所有主基线与种子，不按结果挑选种子。置信区间按题目配对并考虑同一道题跨种子的相关性。

正式验收未通过则如实记录；后续若按正式错误案例继续选参，重新使用独立留出题验证，避免把参与优化的题继续当作独立证据。

## 实验边界与时间安排

保持当前 FastMTP FP4 Target / BF16 草稿层、R39 环境、temperature=0.6、空 system prompt、no-thinking、4096 上下文、1 GiB KV。正式对照使用相同提示词、输出上限、warmup、设备功耗配置与审计关闭设置。修改停止规则或模型加载需要新的协议与全部主基线对照。

旧 test 的 100 题已用于诊断，继续作为回归案例；新正式 100 题在校准和配置冻结后确定。校准、profiling、性能短测和正式测试使用不同结果目录。

按旧记录，三个主基线加 Adaptive 各 100 题的请求耗时合计约 25.3 小时，3 个种子约 76 小时量级；加上优化前质量对照和消融会更长。实际时间取决于输出长度与优化收益，因此先过短测和质量检查，再启动长跑。

HumanEval 在 Docker 访问问题解决后追加；当前阶段的验收限定为 GSM8K，不宣称完成跨任务验证。阶段失败时保留证据并回退该项改动，继续处理下一个已有证据支持的瓶颈。

## 实测后的追加对照

D3 仅裁剪/anchor-only 未改善性能；D4/N12 用于摊薄近似固定的 Target 成本。
若选择 D4 配置，正式阶段同时检查 Native、Cactus、SpecCascade 的 D3/D4，
并补做 D3 + head 优化消融和基线共享 head 优化控制，避免把深度或通用 head 加速
全部归为 Adaptive 规则本身的收益。当前 Cactus 短测已采用相同 D4。
