# Adaptive RAVEN 全项目审查：目标、差距与优化方向

日期：2026-10-07（UTC+8）。状态：**源码、历史实验与 CPU 离线审查完成；新的 GPU profiling、基准复测和优化候选尚未执行。**

本次审查覆盖方法 workers、提案树、验收/残差/随机流、Target 数值适配、MTP/KV、评分统计、后台控制器、预算及文档。证据来自当前源码和已保存的冻结结果；有限现场不能证明所有输入均正确。

执行顺序见 [审查后的优化计划](../plan/adaptive-raven-project-review-optimization-2026-10-07.md)。本次相对上游的修改见 [专门记录](upstream-changes/project-review/2026-10-07.md)。

## 一、我们的目标是什么

**研究目标：在同一模型、同一设备、同一评测协议下，Adaptive RAVEN 相比 Native、Cactus、SpecCascade，正确率和正常完成质量不下降，同时更快、截断更少。**

设备适配是实现这一目标的前提。目前不是只要求“服务能启动”，也不是只要求接受更多草稿 token。需要将 RAVEN 的树状态复用与自适应预算转化为实际收益。

| 对照 | 本仓库中的含义 | RAVEN 要证明的价值 |
| --- | --- | --- |
| Native | 原生 FastMTP 推测解码；不是单独 Target 的自回归生成 | 树与松弛带来的速度收益能抵消额外成本，质量不退化 |
| Cactus | 当前仓库的 Cactus + FastMTP 链实现 | 残差精确命中和状态复用带来额外收益，不能只增加树计算 |
| SpecCascade | 当前仓库的 SpecCascade TokenV3 + FastMTP 实现 | 对另一种接受/级联策略仍有稳定的质量与速度收益 |
| uniform RAVEN | 同类树结构的静态预算版本 | 作为消融，检验 adaptive 分配本身是否有价值；不是第四个主要基准 |

这些名称指本仓库实现的具体变体。论文中的完整模型、训练方式、其他变体与本机适配差异必须列明；不能把本仓库的一个变体推广为原论文所有设置。[Cactus 原论文](https://arxiv.org/abs/2604.04987)；[SpecCascade 原论文](https://openreview.net/pdf?id=vo9t20wsmd)。

### 验收指标

1. **质量优先：**沿用原评分器，同时考察“正常结束且判对”。开发门槛要求总体及每个种子均不下降；正式实验对三个基准逐一报告差值与置信区间。
2. **完成质量：**截断不增加，修复后 72 请求参照的 11 条截断至少减少 1 条；同时报告新增/恢复截断、重复、可信末尾答案。不能通过提前截停或改评分器制造改善。
3. **速度：**同时报告端到端 token/s、平均整题耗时、中位数和 P95。正式吞吐比按题聚类的 95% 区间下界应大于 1，平均整题耗时应更低。初期以追平最快基准并争取至少 5% 吞吐收益为工程目标。
4. **可靠性：**P/Q/H 有限，位置/KV/提交正确，记录可复查；后台有界运行、失败保存现场、无自动重复搜索。

“有限样本没有少判对”不能证明总体正确率绝对相同；未观察到显著差异也不等于证明质量相等。当前不新增可接受的正确率下降额度。达不到全部要求时，应报告部分收益或负结果。

## 二、当前项目究竟处于什么状态

当前使用 FastMTP，Target 为 bitsandbytes FP4 加载，真实物理 MTP 层保持 BF16、head0 递归使用。不是此前 Gemma 方案。继续保持 R39.2.1、PyTorch 2.10 + CUDA 13、vLLM 0.18、BNB 0.50.2、Transformers 4.57.6。

质量/计时协议继续固定：temperature 0.6、上下文 4096、输出上限 2048、TP1、单请求、1 GiB KV、关闭跨请求 prefix cache、原 prompt/no-thinking 和原评分器。

公共数值设置包括统一反量化/BF16 路径、完整 BF16 归约、BNB 固定 64 行、RMSNorm 行上限 255、BF16 LMHead 固定 16 行、TRITON 2D attention、P×V FP32 和 canonical 祖先读取。所有主方法需要统一这些设置并核验实际 worker/backend，不能只比较参数名称。

## 三、方法与实现审查

### 1. 残差精确命中是应保留的核心

当前主模式为 `residual_hit_anchor`：先按既定 H/Q 规则验收；拒绝后先从 `(H−Q)+` 抽样 correction，再按 token ID 查找已验证 sibling；命中时复用其状态并追加一个原 Target token。

这个顺序避免树为了“更好命中”而重新选择 correction。优化应围绕增加有效复用、降低实际成本展开，不能用挑选高分树节点替代原残差抽样。

### 2. 自适应松弛有质量风险，不能以局部一致性代替质量证明

接受和拒绝使用同一个 H，是必要的实现条件；但 H 由候选及整个已验证块的信号构造，并不自动等于原 Target 分布 P。局部 actual-TV 控制也不保证整句答案正确率不下降。

本次 CPU 小词表枚举：P=[0.55,0.30,0.15]、Q=[0.10,0.80,0.10]，delta=0 的输出边缘为 P；delta=1 的该例输出边缘为 Q，与 P 的 TV 为 0.5。这说明松弛可能改变输出分布，是近似方法的性质，**不是新发现的 Cactus 实现故障或对其整篇理论的否定**。

在 1231 的既有现场，低 Target 支持的 `fingers` 确实曾仅因松弛被接受。这能定位局部事件，尚不能单凭一个 token 证明最终错误全部由它造成。新的质量候选应由完整条件证据支持。

### 3. 存在未使用节点和重复计算，但尚无当前实机加速证明

本次新增 [离线审查脚本](../scripts/audit_raven_project.py)，只读取冻结张量与记录：

| 检查 | 实际结果 | 证据边界 |
| --- | --- | --- |
| 29 个真实 B 帧的 anchor 后剪枝 | 节点 224→188，减少 16.1%；58 次 CPU 验收的输出、路径、terminal、决策概率和 RNG 末状态相同 | 使用新 CPU RNG 和保存的 P/Q；不是 live GPU、MTP、Target 或 KV 等价证明 |
| 16 个真实根 Q 的完整排序/精确 top-k | 32 次 CPU 选择得到相同候选与统计 | 不证明所有 ties、CUDA 或端到端加速 |
| 24 个真实 proposal 帧 | 326 行累计 MTP 处理，对应 190 个最终节点 | 仅显示重复物化现象，不证明 136 行都可安全删除或同比省时 |

当前 anchor 验收不会读取 sibling 的后代，但构树仍为它们生成/物化状态。逐层扩展还会重算累计树，最终再物化一次。值得检查的计算复用点主要在这里。

不过，Target 的线性计算固定填充到 64 行，LMHead 固定到 16 行。当前小树删掉一两个节点，可能仍落在同一个填充块内，主要 GEMM 形状没有变。不能把“少 16% 节点”直接换算成“快 16%”。

而且这些方向已经有负结果：2026-10-01 单独剪枝短测约 −3.3%，anchor-only 约 −4.7%；组合 D4/N12/head3/top-k 的短测曾快约 11.3%，完整回归却质量失败。当前数值路径已不同，只有新 profiling 提供理由，才值得重新试。

### 4. 复用 strict 后代是研究方向，先补条件分布证明

`residual_hit_strict` 能继续读取已有备选后代，可能让这些计算产生回报。不过，当前分配器在采样子 token 后，按包含该 token Q 质量的累计路径分数竞争节点预算。**被保留的 child 条件分布未必仍是原 Q。**

因此，“先独立从 Q 抽样，再对留存 child 使用 P/Q”还不足以直接声称分布忠实。此风险是对未来 strict 续走路线的审查要求；当前 anchor 不消费这些后代抽样，不能据此断言当前 anchor 失败。

CPU 玩具枚举使用现有 `level_expansion_order`：两个 recovery parent 争一个剩余槽；Q_A=[0.9,0.1]，Q_B=[0.5,0.5]，A 仅在抽到高概率 token 时留存。P_A=[0.5,0.5]，对留存样本按原 Q 做 strict 验收、未留存则回退 P，输出为 [0.55,0.45]，不是 P。这是选择依赖样本的反例，不是完整生产流水线失败复现。

若研究该路线，应先由父前缀信号决定 continuation 槽，再抽子 token；或推导真实条件提案律及对应残差。预算、命中事件、KV 与抽样顺序都要证明，不能把 strict 开关直接当作质量安全的加速选项。

## 四、截断为什么仍然存在

这里有至少三个不同问题，不能合并成“max_tokens 太小”：

1. 原 P/Q/KV 数值或状态故障。历史上确实发生过，相关现场已修复和有限复测；新轨迹仍需要检查受影响的长状态。
2. 近似 H 及随机路径改变了推导、EOS 或重复行为。全局 cap2 让部分题完成，也让其他题由对变错，说明不是单向改善。
3. 在本机公共 Target/模型/模板下，某些生成本身很难停止。Native 的 1532 三种子失败提示这部分也存在，但还不能排除公共数值实现的问题。

本次分析 1532/seed43 的 B 完整诊断：

- 共 605 轮；现有精确连续 token 后缀重复检测命中 **0** 次。
- 被访问主节点的 Target EOS 总概率最大仅 **1.69×10⁻⁷**；阈值 0.01 的保护没有触发。
- 文本存在反复换说法/重新推导，精确 token 重复检测不容易捕捉。
- 仅把 H 退回 P，不会自动让原本极低的 P(EOS) 变高。

这些是单条轨迹的观测。不能推广成所有截断都由模型导致，也不能把不同 Native/B 输出当作同前缀因果比较。

**下一步必须把两项检查分开：**

1. 对保存的实际晚段前缀，比较当前树 Target 与独立顺序 Target 的 raw logits、温度后 P、EOS、位置/KV，区分公共实现与方法差异。
2. 用独立 Target-only 生成诊断同题长回答，观察不经过 MTP 的结束与重复情况；不同 RNG 路径允许不同输出，不要求逐字一致。

若主要是公共模型/模板问题，提示词、量化或结束协议的调整必须建立所有方法统一的新协议，单独冻结比较。不能把只给 RAVEN 使用的新提示或提前停止归因于 RAVEN 方法。

## 五、性能优化应按什么顺序进行

### 先理解接受长度和轮成本

近似关系为：**解码 token/s ≈ 每轮实际提交 token 数 / 每轮耗时**。MAL 提高而轮成本增长更大，就会变慢。整题更短也可能仅因输出更少，必须和生成吞吐分开。

历史短测的同步 inclusive profile 中，Target 约 937.6 ms/轮、proposal 约 216.1 ms/轮、verify 约 23.5 ms/轮、KV update 约 15.3 ms/轮；其中 adaptive plan 约 3.24 ms/轮，是 verify 内部子项，不能重复相加。

这份旧配置 profile 中，规划只约占 0.3%，即使全删也达不到 5% 总体收益；全部 verifier 也只有约 2%。这些量级提示过去对松弛规划/懒残差的关注过多。**旧比例不是当前新数值配置的组件占比，必须重新测量。**

### 当前建议

| 优先级 | 优化方向 | 判断与限制 |
| --- | --- | --- |
| P0 | 当前数值配置的四方法分段 profiling + 同协议基准复核 | 先取得真实 proposal/Target/同步/KV 成本和质量差距，防止凭 MAL 或旧 profile 选方向 |
| P1 | MTP 累计前缀重算、最终物化、重复父行 logits 的复用 | 最值得检查的 RAVEN 专属成本；必须验证隐藏/KV/形状/完整 Q 与随机流 |
| P1 | 合并必要归一化/检查，减少逐行 `.item()`、`float()`、`.tolist()` 同步 | 同步可能放大 Python 成本；保持有限性防护与相同概率，不删安全检查换速度 |
| P2 | 当前 fixed padding 下重新评估后剪枝/精确 top-k | 有 CPU 等价证据和历史负结果；只有实测收益才推进，不重新盲跑同一方向 |
| P2 | Target 公共 dequant、attention、LMHead 成本 | 可能改善所有方法的绝对速度；所有基准同步应用，不能单独当作 RAVEN 的方法收益 |
| P3 | 在有条件证据时试一项局部松弛风险控制 | 用在线 P/Q 和已提交历史，不读取题号/gold；不再默认全局收紧一定有效 |
| 后续研究 | strict 后代复用 / 成本感知的节点分配 | 可增加有效 token 或减少无效节点；属于方法改变，先完成选择依赖的概率证明和独立质量回归 |

`fixed6_vllm._strict_tree_sampler` 仍无条件计算并转移各行 Target top1，供轮次审计使用；关闭审计时可评估跳过这项工作。其整体收益须测量，不把微小清理称为解决核心速度问题。

GPU 操作异步执行，Python 墙钟、GPU kernel 时间和 CPU 等待应分开。使用 CUDA events、明确同步边界和少量 profiler 范围；有探针运行与正式计时分离。PyTorch 官方说明了异步执行及计时方法，也提醒 profiler 的形状/堆栈记录会增加开销。[PyTorch 2.10 CUDA 语义](https://docs.pytorch.org/docs/2.10/notes/cuda.html)；[Profiler 文档](https://docs.pytorch.org/docs/2.10/profiler.html)。

## 六、实验流程需要修正的地方

1. **参数有名无效：**现有 `Round2.start_server(..., profile=False)` 未把 profile 参数传入有效 env；profile 环境值仍被清空。不能以“传了 profile=True”宣称已计时。
2. **profile 暗含额外调用：**现有 `runtime_profile` 自动运行 top-k 等价检查、预热和计时循环。新 profiling 必须关闭/单列这些检查，并核验 proposal、Target 与嵌套范围。
3. **质量拒绝被归为故障：**当前 cap 的 GateRejected 最后表现为 `STOPPED_FAILURE`，容易误认为运行崩溃。新控制器应区分质量拒绝、数值拒绝、运行故障、预算停止和完成；保存原失败阶段与实际退出记录。
4. **冻结不够分层：**整个 scripts 哈希有助完整溯源，但仅添加分析脚本也会改变总哈希。应保留全源码快照，并添加 Target/MTP/验收/控制器的依赖哈希与有效配置；只在受影响范围内复用证明，不能直接改旧 gate 哈希冒充同源。
5. **缺当前基准：**先用统一 D3/head 行批 1 校准四方法，之后保留原计划对三个基准 D3/D4 的相等选参机会。旧 Native 6 故障配对不能替代完整基准。
6. **预算需要账本：**原表 2684 是混合调用数，含 64 CUDA；主 HTTP 请求为 2620。16 条自然诊断额度已用完；原完整回归 288 已执行 192，剩 96；懒残差和 cap 已占两个候选名额。其他独立修复单元与预热另列，不能混为原表全部消耗。

旧目录、冻结文件、负 gate 和失败记录保留。新诊断或候选需要新的有限单元/明确预算调整，不自动把未执行的 96 条改作其他用途。

## 七、我的总体判断

**适配已经使项目能够运行，局部实现故障已修复；研究目标尚未达到。现在最需要的是当前配置的成本证据和公平基准，而不是继续叠加全局概率限制。**

近期主线应是：把 RAVEN 已经做过的计算更有效地复用，尽量保持生成概率与质量轨迹；截断另以同前缀 Target 检查和 Target-only 诊断定位。方法级自适应、深度或节点策略只有在明确原因后才改变。

如果当前模型/设备组合下最终无法同时胜过三个基准，应如实划定优势范围，保留负结果。这不由调低质量要求或反复使用测试题来解决。
